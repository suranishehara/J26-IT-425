# Intent and entity data collection

## Current checkpoint

28 explicit assistant-authored starter messages: four per intent, with 14 train and 14 development records. Labels were written explicitly, not generated by the rule parser. Entity labels include canonical value and negation. Spans are derived from the annotated exact mention and validated against normalized text. These examples exercise annotation tooling and expose rule weaknesses; they are **not real participant data, independent evaluation or sufficient evidence for a robust trained model**. No intent/NER model has been trained or activated at this checkpoint. No production parser changes were made.

Files:

- `data/nlu/starter.json`: complete author-written labels.
- `data/nlu/collection_template.json`: deliberately unfinished template for permitted real messages. Pending records cannot enter exports/evaluation.
- `scripts/prepare_nlu_data.py`: annotation validation, normalized-span export and unchanged rule-baseline comparison.

## What to collect next

Ask volunteers to write natural fashion questions and follow-ups in their own words, without copying the starter sentences. Collect only messages they authorize for university research. Do not include names, contact details, private health information, photographs or unnecessary body measurements. Assign pseudonymous contributor IDs outside the text if needed for approved study tracking; do not infer demographics. Keep consent/permission documentation separately under your institution's process.

A practical initial target is **30–50 independently written examples per intent** (210–350 total), plus 20–30 short complete dialogues for later state evaluation. This is a starting collection target, not a statistical guarantee of model quality. Include global, Sri Lankan/traditional and mixed questions; synonyms, misspellings, negations, budgets, ambiguous references and unsupported topics. Do not obtain class balance by copying one sentence and replacing fabric names.

Keep near-duplicate/paraphrase families and every turn of a conversation in the same split. Prefer contributor-separated splits where feasible. Assign roughly 70% train, 15% development and 15% reserved final test at the group level, while checking intent coverage. The starter's tiny 50/50 split is for mechanics only. Put independently collected final tests in a separate locked file; the current development exporter deliberately accepts only train/dev. Do not inspect final labels to tune rules or model choices. Exact-text/family-ID checks cannot discover all semantic duplicates; reviewers must group those.

## Intent annotation guide

| Intent | User goal | Example |
|---|---|---|
| recommend | Obtain outfit/design options | “Help me pick something for work” |
| explain | Understand an existing choice/ranking | “What made you choose that?” |
| compare | Contrast two or more alternatives | “How does cotton differ from silk?” |
| update_preferences | Correct/add/remove an existing constraint | “My budget is now 8000 rupees” |
| knowledge_question | Ask a general definition/fact | “Describe handloom weaving” |
| greeting | Social opening without a fashion task | “Good morning” |
| clarify | Insufficient information or unresolved reference | “The other one” |

Use one primary goal for this baseline. Multi-intent examples require annotator discussion; preserve the secondary goal in notes for future schema expansion rather than silently forcing a questionable label. Annotation reflects user intent, not which keyword the current rules recognize. For follow-ups, read the complete conversation before deciding. A model trained only on isolated text cannot resolve all context-dependent labels.

## Entity and slot annotation

The initial entity type is `fashion_term`, aligned with the existing parser's ontology: garments/material terms and batik/handloom/Osariya aliases. This is not a complete learned NER ontology. Add separate entity types for occasion, currency, measurement, etc. only with a versioned schema and baseline alignment.

Each entity needs an exact `mention`, canonical `value` and boolean `negated`. Example: `{"mention":"Kandyan saree","value":"osariya","negated":false}`. For “avoid silk”, annotate silk with `negated:true`. For repeated identical mentions specify each entity's `start` in the normalized text; never assume the first occurrence. Offsets are half-open `[start,end)` in NFKC/casefold-normalized text, not the original raw string. Spans must not overlap. Labels such as value or negation are human annotations; the exporter only locates the supplied mention.

Annotate scalar slots explicitly: occasion (wedding/office/festival/casual/temple), weather (hot/cool/rainy), setting (outdoor/indoor), style (traditional/formal/casual/western), colours (normalized list, e.g. grey), budget_lkr (positive numeric LKR). Unknown/unstated slots are omitted, not guessed. `remove_slots` names explicit removals, e.g. budget_lkr. Terms/excluded_terms derive from the explicit entity labels. Do not treat a negated garment as a requested garment.

Two reviewers should independently annotate real data, reconcile disagreements and retain the original labels/notes to measure agreement. In collection records set `annotation_status` to `reviewed`, list pseudonymous `reviewer_ids`, and set `permission_confirmed:true` only after permission is documented. The validator blocks explicitly pending/unpermitted records, but cannot establish actual consent or verify reviewer quality. Starter records have author provenance rather than fictitious participant/reviewer claims.

## Validate and record the baseline

From the Component 4 folder:

```powershell
.\.venv\Scripts\python.exe scripts\prepare_nlu_data.py --output runtime\evaluations\nlu_starter_01
# For your reviewed collection, use a new directory:
.\.venv\Scripts\python.exe scripts\prepare_nlu_data.py --input data\nlu\collected_reviewed.json --output runtime\evaluations\nlu_collection_01
```

The second command requires you to create that reviewed collection first. Existing output directories are never overwritten. Export records include validated normalized spans; reports include source/rules hashes, split counts, intent accuracy, macro-F1 across seven fixed labels, confusion matrices, entity micro precision/recall/F1 requiring exact span + canonical value + negation, and full slot/removal exact match. Empty-entity precision/recall use zero for zero denominators; support counts are included. This does not yet evaluate multi-turn state accuracy. No fictitious human ratings are filled in.

## Training gate

### First recorded starter baseline

`runtime/evaluations/nlu_starter_01/baseline_report.json` records 14/14 correct training intents and 3/14 correct development intents (development macro-F1 0.1122); full slot/removal exact match was 13/14 on development. Training examples intentionally exercise familiar rule patterns; development examples include harder paraphrases. This small, constructed contrast is a diagnostic, not an estimate of deployment accuracy or evidence for any replacement model. Failure cases were retained without modifying the production rules. All 43 software tests pass; software-test success does not mean NLP predictions are accurate.

Once real reviewed train/dev data has adequate coverage, implement a learned intent baseline (e.g. TF-IDF with a linear classifier) and compare it with unchanged rules on the same development split. Evaluate a token/entity model separately; learning intent does not automatically learn entities. Keep training isolated from the production parser and report class imbalance, group splits, per-class errors and uncertainty. Select hyperparameters on development only, then freeze and run the independent final test once. Do not claim the 28 author-written starter messages prove generalization.
